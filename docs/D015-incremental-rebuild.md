**基線**：`e6e4e67`
**參考**：本卡不從實驗線搬規則、數字或畫法（純 3D 端的效能工程），所以沒有實驗線 commit 要對。

## 為什麼做這張

1. **D014 讓播放中重建變多了。**
   - 為了「t＝3 開始長高時樓體一定在」，屋齡 ≥ 2 的工地還沒有樓體就重建。
   - 起步城播放 60 天重建 20 次，大約三天一次；舊規則最多五天一次（D014「沒做成的事」2）。
2. **每次重建都整座城重做、整份重傳。**
   - 每個街區、每棟建築的幾何重新產生一次，頂點資料全部重新上傳 GPU；地面貼圖也是整張新建、整張重傳。
   - 其實大部分沒變：起步城播放 120 天、重建 31 次，街區計畫逐塊比，只有 230／2,183 塊（10.5%）是新的，一次 0–15 塊。
3. **手機上會頓。** 主執行緒上一次重建的 JS 在 6 倍降速下約 70–130 ms，中階手機上大約掉幾幀、每三天一次（1 倍速）。

## 施工前查到的事（雲端容器、Chromium 141、6 倍降速、起步城播放 60 天）

- **重建那一步的分段**（中位數，播放那條路 `__gt.advanceBy` 連續推）：
  - 建場景 129–136 ms：街區計畫 1–17、地面貼圖 11–24、地面網格 2、建築幾何 49–51、施工屬性 4、轉成網格與統計 22–25、樹 9–10。
  - 每天同步工地 11–12 ms（每天都有，不是重建才有）。
  - 重建之後第一次作畫 97 ms（平常一幀約 3 ms）。
- **作畫那一段會被 SwiftShader 放大**：連續推、不等畫面時，軟體 GPU 積了好幾幀的工作，第一次作畫最久等到 1.4 秒。照畫面節奏真的播放（rAF）時，平常一幀就要 83 ms（軟體 GPU 畫陰影和整座城），重建那一幀多出約一幀。所以本卡判的是主執行緒上的 JS 時間與上傳量，不判 SwiftShader 的作畫時間。
- **著色器程式、幾何、貼圖數量**：重建前後都是 18／13／8，沒有重編、沒有漏。
- **一次重建上傳多少**（建築頂點；牆每頂點 19 個浮點數，其他、點綴 14 個）：
  - 起步城第 60 天：牆 2,186、其他 1,042、點綴 6,146 個三角形，1.71 MB；第 120 天 1.93 MB。
  - 另加地面貼圖 576×576×4＝1.33 MB，整張重傳。
  - 種子城 7.46 MB、AI 城 3.87 MB（只能看，不會重建，只有開城時傳一次）。
- **three.js 0.186 可以只上傳一段**：`BufferAttribute.addUpdateRange`、`Texture.updateRanges`（逐列）。

## 做什麼

### 1. 建築幾何照「件」快取

- 一件＝一個街區、一棟不走街區的建築（非住商工、`?blocks=off` 的住商工）、全部高架路合成一件。
- 每件有一把鍵：決定它幾何的全部輸入。街區是位置、寬高、種類、等級、變體、地基高、畫法檔（逐戶立面開不開）；建築是編號、種類、等級、變體、位置、大小、地基高、廢棄。
- 鍵沒變就沿用上一次產生的：頂點資料、施工屬性（`aCon`）、每格最高點與牆頂的貢獻、前庭樹、點綴件數、錨點、包圍盒、窗樣式統計、風化牆數、近看小物的底稿。
- 近看小物照舊每次重算要不要畫（看街區起點那棟的屋齡，會自己變），底稿沿用。
- 快取只留這一次用到的件，換下來的就丟。

### 2. 牆、其他、點綴三個網格改成常駐、分段更新

- 三個網格各一份常駐的頂點緩衝，每件佔一段。
- 件換掉：舊的那段清成退化三角形（不畫、不投影子、點不到），新件先找放得下的空洞，放不下接在尾端。只上傳改到的那幾段。
- 尾端有件、前面有放得下它的空洞時，把它搬進空洞，縮短要畫的範圍。
- 容量不夠時放大 1.5 倍，整份重傳一次。
- 點擊用的「每個三角形屬於誰」照件更新。街區的編號照這一次的計畫重寫。

### 3. 地面貼圖常駐

- 同一張貼圖，只上傳變動的格：每格 S 列，一列一段。
- 變動的格超過一半、或第一次建，就整張傳。

### 4. 野樹沒變就沿用

- 樹的位置、種類沒變時沿用上一次的實例資料，不重傳。
- 前庭樹照舊每次重排（照這一次的計畫順序，很小）。

### 5. 什麼時候整張重來

- 開城、換城、換畫法檔、換明暗，照舊整座城從頭建（快取清空）。
- 首次建的三角形順序跟現在一樣：先非街區建築（照城市的建築順序），再街區（照計畫順序），最後高架路。

### 6. 順手

- `timing.plan` 一直是 0（起點與終點取在同一刻），改成真的量街區計畫。
- 測試出口：場景的逐位元組摘要、不分順序的摘要、這一次重建重做了幾件、上傳了多少位元組、強制整張重建。

## 不改什麼

- 模擬、規則、存檔、分享碼、世界歷史都不動（規則 2、4）。
- 什麼時候重建不改：還是「有新建築或升級、而且隔了 5 天」或「屋齡 ≥ 2 的工地還沒有樓體」（D014）。
- 畫面不改：同一座城、同一個鏡頭，增量建的畫面要跟整張重建逐像素相同。
- draw call 數不改。
- 300 年示範（`?mode=history`）不動。

## 驗收（動手前寫）

1. **首次建逐位元組不變**
   - 動手之前先加摘要出口，用本卡基線的建置錄黃金樣本：種子城（A、B、C、off 四檔）、AI 城、全種類、新城、起步城第 0／60／120 天。
   - 摘要包括：牆、其他、點綴每一種頂點屬性（含 `aCon`）照畫的順序、每個三角形的主人與牆頂、地面貼圖、每棟包圍盒、點綴件數、近看小物件數、窗樣式統計、畫到的街區、非住商工用色、風化牆數、施工資料（最高點、地基、牆頂、街區編號）、前庭樹與野樹的實例資料。
   - D015 之後首次建全部等於黃金樣本。
2. **增量建＝整張重建**
   - 起步城走播放那條路 60 天、劇本城（D011 那一串施工，會拆會蓋），每一次重建之後比：增量建的場景跟同一座城清空快取整張建，摘要（不分三角形順序、照主人分組）相同。查詢出口的結果（點擊、包圍盒、件數……）相同；地面貼圖逐位元組相同。
   - 所有不屬於任何一件的三角形都是退化的；要畫的範圍之外沒有件。
   - 注入錯誤要紅：鍵少了地基高、換下來的段沒清、街區編號沒重寫，各一個突變。
3. **畫面逐像素相同**：起步城第 30、60 天，預設鏡頭與拉近（近看小物開）各一張，增量建＝整張重建，不同 0 像素。
4. **只做變動的部分**（起步城播放 60 天，每一次重建）：
   - 重做的件數：中位數 ≤ 全部件數的 20%。
   - 上傳的位元組（建築三個網格＋地面貼圖）：中位數 ≤ 整份的 15%。容量放大那幾次另外列出來，照實記。
5. **主執行緒時間**
   - 同一台機器、本卡基線跟 D015 交替各跑兩輪，起步城播放 60 天、6 倍降速，一次重建的 JS（建場景＋同步工地）中位數至少降一半。前後數字記在卡上。
   - 煙霧另判比值（不看機器快慢）：同一頁裡增量重建的 JS 中位數 ≤ 整張重建的 50%。
6. **手機預算不變**：draw call 數不變；D014 的兩個預算情境（起步城工地最多那天、AI 城）三角形（含空洞）≤ 118,884、draw call ≤ 20；首次建的三角形釘值（D004–D014）照舊。
7. **不漏**：起步城播放 60 天，快取的件數＝這一次的件數；`renderer.info` 的幾何、貼圖、著色器程式數量不增加。
8. 本機型別、Node 守衛、建置、煙霧全綠；main 的 Actions 綠。

### 卡面更正

1. **驗收 2 的「鍵少了地基高」在瀏覽器抓不到**
   - 播放、劇本走得到的狀態裡，同一塊地界的地基高不會變：建築格不會是路或水，高地也不會變。所以播放、劇本、畫面三段在這個突變下全綠，它是等價突變。
   - 「鍵少了等級」也抓不到：升級時變體、街區切分通常一起變，鍵本來就換了。這一個不是等價的，只是 180 天裡沒碰到。
   - 所以另加 Node 守衛（`tools/unit-d015.mjs`），不靠碰運氣：拿真的街區、非住商工建築，一次改一個輸入重畫，幾何變了鍵就一定要變；每一項都要有改了會變的例子。鍵少了地基高、等級、變體（街區）與變體、大小（非住商工）都抓得到，原始碼上改鍵的兩個突變也跑過一次，都紅。
2. **非住商工的等級**：造型表畫的 183 種，等級改了幾何都不變（高度、五色只看種類與變體）。鍵照樣帶著等級，守衛這一項只記不判；「非住商工鍵少了等級」是等價突變，換成「少了變體」。
3. **驗收 3 的「預設鏡頭」改成整張地圖的鏡頭**：拍增量那一份時要先拍兩個鏡頭再整張重建，拉近之後回不到開城時的鏡頭，所以兩個鏡頭都用 `__gt.view` 設（整張地圖 0.9 倍、拉近 5 倍）。
4. **D010、D012 的「重建一次場景」改量整張重建**
   - 這兩項原本呼叫 `__gt.simRebuild()`。D015 之後城沒變時它是空轉的增量重建，量到 26 ms，已經不是那兩項要量的東西。
   - 改成 `simRebuild(true)`（清空快取從頭建，就是開城時的最壞情形）。播放中的增量重建另由 D015 播放段量。
5. **驗收 7 的幾何數量允許多一件**：工地網格每天換，數量會上下一件。
6. **驗收 5 的煙霧比值不含容量放大那幾次**：放大那一次整份重傳，是另一種成本，驗收 4 另列。

### 施工中遇到、照實記下

1. **量法本身會騙人**：研究時連續呼叫 `advanceBy`、不等畫面，SwiftShader 積了好幾幀的工作，重建之後第一次作畫最久量到 1.4 秒。照畫面節奏真的播放時，重建那一幀只多出約一幀。卡面判主執行緒的 JS 與上傳量，就是因為這個。
2. **首次建一次就逐位元組相同**：10 個情境第一次比就全等。建築的畫法只改累積器上的主人與牆頂、都有還原，一件一個新累積器畫出來的跟整張共用一個一樣。
3. **畫面那一段第一版比錯了**：拉近那一張是在上一張整張重建之後才拍，比的是整張對整張（空洞 0）。改成兩個鏡頭都先拍增量那一份。
4. **Node 只去型別，不收建構子參數屬性**：`Arena` 第一版用了 `constructor(readonly spec…)`，`construction.ts` 引用它之後 D014 的 Node 守衛也跟著載不進來。改成明寫欄位。
5. **自己把沒提交的修改蓋掉一次**：驗突變時用 `git checkout` 還原檔案，連同還沒提交的兩處修改（鍵的三個函式、建構子）一起還原掉。當場照原樣補回、型別與守衛重跑都綠、立刻提交；之後驗突變改成先備份再還原。
6. **場景裡還有施工預覽**：旁邊另建的那一份場景少了施工預覽的實例網格，摘要差一項。摘要時把預覽借過去、摘完放回。
7. **野樹的鍵本來是串字串**：幾千棵樹每次重建都串一次，6 倍降速下約 3.5 ms。改成兩個數字雜湊。
8. **改守衛時把 `finally` 註解掉了**：`7d8c7cd` 在 `try { … }` 同一行後面加註解，把後半的 `finally { … }` 也變成註解，煙霧整支載不進來（`tools/smoke.mjs`、`tools/smoke-d011.mjs`）。最後一輪煙霧第一次跑就是這樣紅的；註解移到上一行、五支工具都 `node --check` 過，再整輪重跑。
