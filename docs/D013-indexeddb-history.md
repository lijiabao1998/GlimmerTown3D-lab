## 為什麼做這張

- 「我的城」現在整座存在 localStorage：實驗線格式的分享碼，本線的世界歷史塞在附加欄位 `d3.r`（每筆約 18 字元）。
- 兩個問題（D011 量的）：
  1. **有上限**：分享碼上限 2,000,000 字元，歷史約 8 萬筆就存不下；現在超過就不存、跳提示，玩家只能匯出。
  2. **越玩越慢**：每一筆手勢都把整份歷史重新編碼、整張寫回去，時間跟歷史長度成正比（桌機 1 萬筆 17.7 ms、8 萬筆 107.6 ms）。
- 世界歷史是三種玩法共用的地基（CLAUDE.md），不能因為長了就不存。

## 施工前查到的事

- 存檔的路：`src/cityView.ts` `saveNow()` → `src/io/save.ts` `saveCode()`（整張重編、`packHistory` 整份歷史）→ `localStorage.setItem('gt3d.v1.save')`；每一筆手勢、每一天（不在播放時）、切到背景都存。
- 讀檔的路：開頁同步讀 localStorage → `loadCode()` → 解 `d3.r`（hv 2）或 `d3.h`（hv 1）→ 重播、跟存檔逐格核對，對不上就退回只用存檔（歷史從這張碼重新起算）。
- 匯出分享碼：整張碼（帶 `d3.r`）；超過上限時給不帶歷史的碼並講明。
- 歷史的緊湊列（hv 2）是**差值編碼**：每一列的天數、手勢編號都是跟上一列的差。所以新加的列可以接著上一次的差值往下編，串起來跟整份一次編逐列相同。
- Node 沒有 IndexedDB：日誌要有一層介面，瀏覽器用 IndexedDB、Node 守衛用記憶體版。

## 做什麼

1. **日誌**（新檔 `src/io/journal.ts`，純邏輯＋存放介面）
   - 一座城一個日誌編號；一列一筆（hv 2 的緊湊列），照順序號存，**只增不改**。
   - 接續編碼：記住上一次編到哪（筆數、上一筆的天數與手勢編號），新加的事件接著編，不重編整份。
   - 滾動雜湊：每一列接著上一個雜湊算（FNV-1a），存檔記下「前 n 列的雜湊」；讀檔照同樣的算法核對，前 n 列對不上就不接。
   - 存放介面兩種：瀏覽器 IndexedDB（資料庫 `gt3d`，物件庫 `journal`，鍵＝[日誌編號, 順序號]）；記憶體（Node 守衛）。
2. **存檔**（`src/io/save.ts`、`src/cityView.ts`）
   - localStorage 照舊放實驗線格式的分享碼（目前狀態：格子、建築、資金……逐欄照實驗線），`d3` 改成 **hv 3**：`{ f, s, g, hv: 3, j: { id, n, h } }`——日誌編號、筆數、前 n 列的雜湊，不再放歷史本身。
   - 每一次存：先把還沒寫的列一次附加到日誌（一筆交易），交易完成才寫 localStorage。寫到一半關頁：localStorage 還是上一次的狀態，日誌多出來的列讀檔時用不到（前 n 列照樣核得過）。
   - 同一時間只跑一次存檔；存檔中又有新的存檔要求，等這一次完了再存一次。
   - 開新城、清存檔：舊的日誌整份刪掉。
   - IndexedDB 不能用（隱私模式、被封鎖、打不開）：退回 hv 2（整份歷史塞在 `d3.r`，D011 的做法、有上限），狀態列講明。
3. **讀檔**
   - hv 3：開頁先非同步讀日誌前 n 列、核雜湊、解列、重播、跟存檔核對（跟 hv 2 同一套）；讀不到或對不上，退回只用存檔並講原因。
   - hv 2、hv 1 照讀（規則 4）；下一次存檔時整份搬進日誌、改寫成 hv 3。
   - 開頁要等日誌讀完才開城：開頁流程改成非同步；讀的時候畫面照舊（先開樣本城的畫面不做）。
4. **匯出分享碼**：照舊帶整份歷史（hv 2，實驗線與本線都讀得回來）；超過上限照舊給不帶歷史的碼並講明（這是分享碼本身的上限，不是存檔的上限）。
5. **比這一版舊的程式讀 hv 3**：D011 起的讀檔遇到不認得的 hv 會「只用存檔」，城照樣開得起來，只是歷史從那張碼重新起算。

## 不改什麼

- 實驗線格式的欄位一個都不動：localStorage 那一份貼進實驗線照樣能開（規則 9）。
- 歷史事件的種類與欄位不動（緊湊列 hv 2 的編法原樣，hv 3 只是存的地方換了）。
- 模擬、畫面不動。

### 卡面更正

1. **存檔的先後反過來了**：卡上寫「先附加到日誌，交易完成才寫 localStorage」，做的是**先寫 localStorage（帶尾巴）、再附加**。
   - 原因：localStorage 是同步的，IndexedDB 是非同步的；切到背景、關頁那一下只來得及做同步的事。
   - 先附加的話，那一下存的只能是舊狀態。現在 localStorage 那一份永遠自己就夠：日誌裡已確定的前 n 列，加上它自己帶的尾巴。
   - 所以 hv 3 多一個欄位 `t`（尾巴）。卡上的 `{ f, s, g, hv: 3, j }` 少寫了它。
2. **「同一時間只跑一次存檔」**：存檔本身是同步的，不會重疊；會重疊的是附加，所以改成「同一時間只有一筆附加」，完成之後再存一次。
3. **「施工前查到的事」寫錯一處**：不是每一天都存。播放中每 5 天存一次（`SAVE_DAYS`），另外每一筆手勢、暫停、切到背景時存。煙霧測試照實際的做法推 5 天。
4. **驗收 2、3 的量**
   - 驗收 2：卡上寫「約 12 萬筆以上」，實際灌到 90,001 筆，hv 2 就已經 2,170,956 字元、超過上限（灌的是改分區，每列比平均長）。
   - 驗收 3：卡上寫「1 萬筆與 10 萬筆」，實際量 10,001 與 90,001 筆（同一份灌好的歷史）。
5. **狀態列怎麼講**：卡上只寫「狀態列講明」，做成一顆晶片「⚠ 歷史有上限」。

### 沒做成的事

1. **IndexedDB 某一次開頁打不開時，那一次歷史從存檔重新起算，原本的日誌接不回去**：它留在 IndexedDB 裡（沒刪），但沒有救回來的路；之後存的是 hv 2、新的起點。煙霧測試裡封鎖前那一條 266 列就這樣留著。
2. **沒人要的日誌不會自己清**：只有開新城、清存檔會刪舊日誌；讀檔退回只用存檔、附加失敗改回 hv 2 時，舊的那一條留著佔空間。
3. **開頁時間沒改、也沒量**：這張只讓「存檔」不跟歷史長度成正比。開頁照舊讀整條日誌、重播整份歷史，歷史越長開頁越慢；瀏覽器裡 9 萬筆開頁要多久沒量。
4. **兩個分頁同時開我的城沒處理**：兩邊各自往同一條日誌寫、會互相蓋掉列，下一次開頁雜湊對不上、退回只用存檔。D011 起 localStorage 本來就是後寫的贏，這張沒有改善。
5. **沒有向瀏覽器要「持久儲存」**（`navigator.storage.persist()`）：儲存空間緊時瀏覽器可能把資料清掉。Firefox 要會跳詢問框，沒加。
6. **寫到一半關頁只在 Node 驗過**（記憶體版存放：日誌多了列、少了列）；瀏覽器裡沒有真的在附加途中殺掉分頁。
7. **匯出的分享碼照舊有上限**：歷史長到超過 200 萬字元時，匯出的碼不帶歷史（分享碼本身的上限，卡上本來就不改）。
8. **沒上實機**：Android Chrome、iOS Safari 的 IndexedDB 沒試過。
