# D102 — 煉鋼廠加速施工記進世界歷史（修「讀檔退回快照」的根因）

> 卡號：D101 之後下一個沒用過的號。分支 `fix/d102-steel-history`，疊在 D100（PR #55，head `b328a07`）上；
> D100 合併之後改成以 main 為基底。驗收條件寫在動手之前（CLAUDE.md 規則 6），本節以下到「施工紀錄」之前不再改。

## 業主 2026-11-04 的決定

- D101 的 O7（有運輸的存檔讀不進來怎麼辦）業主選了「**先修根因，再明確失敗**」：先開這張卡修好會自然觸發「退回快照」的鋼鐵加速屋齡對不上，
  D101 才讓有運輸的存檔在讀檔失敗時明確報錯。
- 編號（規則 9）業主選了「**D102 拿 25，交通、市民各順延一號**」：
  **事件 25／`CITY_FORMAT 11`＝本卡的煉鋼廠加速施工**；交通改成事件 26／格式 12；居民改成事件 27／格式 13。
  理由：讀檔規則是「格式比我新就不讀」（`src/io/save.ts:301`），所以先上線的要拿小的號；目前沒有任何玩家存檔用到 25，改號不用遷移。

## 已證實的根因

**機制（讀程式碼）**：
- `src/sim/rules/economy.ts:299-313` `steelConstruction`（實驗線 `d23c18d` 的 55655–55672，D025 搬過來）：有煉鋼廠時，
  每天最多 `min(煉鋼廠數×2, 鋼庫存)` 棟「屋齡 < 9 的施工中建築」額外 `age++`（第 309 行）。由 `src/sim/day.ts:418` 呼叫，在升級（417）之後、合併（430）之前。
- 這個 `age++` **沒有記成任何歷史事件**：`syncCity`（`day.ts:562-592`）只記生長、升級、合併。
- 重播（`src/sim/replay.ts`）的屋齡全靠「起算屋齡 ＋（結束日 − 起算日）」推（第 6-8 行）。所以被加速過的建築，重播出來的屋齡比存檔裡的小。
- 讀檔時 `mismatch()`（`save.ts:335-350`）先比 `cityStats`（`roots` 帶屋齡，`src/sim/city.ts:181`），屋齡一不同就回「對帳數字不同」，
  走 `only()` 退回快照：墓碑、建築編號、蓋起日、歷史全部從這張碼重新起算。

**實測**（本卡的探針 [`docs/evidence/D102/probe-pre-d102.mjs`](evidence/D102/probe-pre-d102.mjs)，結果 [`probe-pre-d102.json`](evidence/D102/probe-pre-d102.json)；
程式碼＝main `18a718c`，D100 沒改這些檔）。d036 的五座城，各 100 次「過一天＋存檔＋讀檔」：

| 城 | 現行程式 | 同一份存檔、讀檔時不比屋齡 | 鋼鐵加速關掉（`const cons = 0;`） |
|---|---:|---:|---:|
| W1／W3／W5 | 0 次退回 | 0 | 0 |
| W2 | **47 次**（第 5 次第一次退回） | 0 | 0 |
| W4 | **48 次**（第 2 次第一次退回） | 0 | 0 |

- 95 次退回的原因字串全部是「歷史跟存檔對不上，只用存檔：對帳數字不同」；每一次都是 1–2 棟、快照比重播**剛好老 1 天**；
  同一份存檔換成不比屋齡的讀法，95 次全部重播成功。
- W2 的 47 次跟 D046 卡（`docs/D046-commission-reliability.md:32`）記的一致；第 5 次首退跟 `tools/unit-d046-fallback.mjs:81` 的 `first === 5` 一致。
- 結論：在這五座城上，**鋼鐵加速是唯一的自然觸發源**（已證實）。推論（未證實）：任何有煉鋼廠、還在長的城都會碰到——
  鋼材的進口目標固定是 12（`economy.ts:232`），有貿易額度的城庫存幾乎不會是 0。

## 修法

1. **新事件 `hasten`（碼 25、城市格式 11）**：一天一筆，列＝`[25, dDay, id₁, id₂, …]`，尾巴是當天被加速的建築編號，由小到大、不重複、至少一個。
   跟合併（碼 17）的尾巴寫法一樣；`hv` 照舊是 2／3（列的編法沒變）。
2. **記錄（`src/sim/day.ts`）**：在升級（417）和加速（418）之間抄下 `tickBld` 每格的屋齡，加速之後屋齡變了的就是被加速的那幾格
   （`steelConstruction` 每格最多走一次、每次 +1）。第 418 行與 `economy.ts` **一個字都不改**（實驗線對拍的錨點，`tools/unit-d025.mjs:605-608`、`tools/unit-d025-live.mjs:183`）。
   `syncCity` 在升級事件之後、合併事件之前推一筆 `hasten`（同一天的 tick 順序：生長 → 升級 → 加速 → 合併 → 災禍）。
3. **重播（`src/sim/replay.ts`）**：清單上每棟的起算屋齡 +1。嚴格驗：編號要存在、還沒拆、那一刻的屋齡 < 9；不合就丟例外（照舊走「歷史重播失敗」退回，不猜）。
4. **存讀（`src/io/save.ts`、`src/io/journal.ts`、`src/sim/eventRegistry.ts`、`src/sim/city.ts`）**：登記、編碼、驗型別。
   **只有歷史裡真的有 `hasten` 的城才寫 `f=11`**；沒有的城，存出來的碼逐位元組不變。
5. **`src/cityView.ts` 只動型別**：地塊歷史的 `LotEvent` 把 `hasten` 排除（它沒有座標，跟 `cms` 一樣）；不加任何畫面。
6. **不放寬比對**：`mismatch()` 不加屋齡容忍。真的不符照舊退回（D046 拒絕過放寬，`save.ts:287`）。
7. **lease**：D100 之外再包一層 D102 lease（D090 的 `modified{before,beforeSha256,afterSha256}` 寫法），`before` 是 D100 的位元組；
   `D084_CHANGED` 擴成包含本卡改的檔，讓 `unit-d066…d081` 的「只准改已核准的繪製檔」照既有的路放行。

## 凍結的驗收（每一條都要有可重跑的斷言）

1. **自然觸發歸零**：W2、W4 各 100 次「過一天＋存檔＋讀檔」**0 次退回**；每次都 `replayed === true`、起始碼不換；
   讀回來的屋齡等於存檔的屋齡（含墓碑）；歷史裡 `hasten` 的編號總數 ＝ 每天 `steelConstruction` 回傳值（`constrSteelUse418`）的總和，而且 > 0。
2. **沒碰到加速的城逐位元組不變**：W1、W3、W5 與現有的起始城，同樣的輸入存出來的碼與 D100 head 的輸出**逐位元組相同**（`f` 照舊依歷史內容是 4–10）。
3. **實驗線對拍不變（規則 8）**：`economy.ts` 與 `day.ts:418` 位元組不變；`unit-d025` 的實驗線黃金樣本（施工耗鋼、逐格屋齡）照舊全過；
   不經讀檔的連續模擬，G8／W2／W4 每天的 `simHash` 與 D100 head 的 `day.ts` 逐日相同（歷史不進 `simHash`）。
4. **重播單元**：人造歷史各一條——升級當天被加速（起算 0 → 1）、生長當天、匯入的、加速之後同一天被合併（墓碑屋齡含這 +1）、
   加速之後同一天被燒毀；每一條重播的屋齡都等於模擬的屋齡。
5. **竄改照舊攔住**：不存在的編號、已拆的、重複或沒排序的、空清單、非整數、那一刻屋齡已 ≥ 9、宣稱 `f=10` 卻帶 `hasten`、`f=12`（比這一版新）——
   每一種都不重播、退回快照，原因字串講得出是哪一種；退回後下一次存讀照常重播。
6. **格式**：`CITY_FORMAT === 11`；登記 26 種；碼 0–24 的碼、格式、欄位跟 D046 的表逐項相同；`hasten` 的列 pack／unpack 往返逐位元組穩定；
   `hv 3` 日誌接續編碼跟整份一次編逐列相同。
7. **突變控制（守衛要能抓到壞的）**：(a) `day.ts` 拿掉記錄 → W2 又退回（> 1 次，重現舊行為）；(b) `replay.ts` 不處理 `hasten` → 重播失敗；
   (c) `hasten` 排到合併之後 → 同日合併的墓碑屋齡對不上；(d) 記錯一棟 → 對不上。
8. **D046 的舊守衛**：`tools/unit-d046-fallback.mjs` 第 1、2 項現在斷言「會自然退回」（`falls > 1`、`first === 5`、`exceeded === 11`）。
   改成：第 1 項斷言 0 次退回，並用「拿掉記錄的 `day.ts` 變體」把舊的 `falls > 1` 留成突變控制；第 2 項改用同一個變體造出真的失配，
   繼續證明 D046 修的起點套娃（`first === 5`、`exceeded === 11` 不變）。第 3 項不動。寫死格式的三處
   （`tools/unit-d010-sim.mjs:80`、`tools/unit-d019.mjs:260`、`tools/unit-d046-history.mjs:97-98` 等）照 D040、D045 的先例原地改成 11／26。
9. **lease 負控**：沒宣告就改、少一檔、多一檔、重複、`after` 雜湊錯、`before` 過期、未知路徑——每一種都紅，錯誤字串保留「exact allowed source」。
10. **全套**：`tsc --noEmit`、`npm run build`、Node 24 的 `npm run unit -- --partition=historical` 全綠；PR 上 `ci`、`transit`、D083／D086–D090 native 全綠。
11. **大小**：W2、W4 100 天後的存檔長度記在卡上，遠低於 `SAVE_LIMIT`（2,000,000 字元）。

### 前面凍結文字裡的錯（不改原文，更正在這裡）

- 根因段說「鋼材的進口目標固定是 12（`economy.ts:232`）」不精確：`steelBase482 = ceil(12 × max(煉鋼廠利用率, 造船廠利用率))`，
  目標還要加上施工需求與造船用量（`economy.ts:231-233`）；企業層沒就緒時利用率是 1，所以基礎量是 12。結論（有煉鋼廠、有貿易額度的城庫存很少是 0）不變，仍是推論。
- 驗收 4 寫「每一條重播的屋齡都等於模擬的屋齡」：人造情境比的是照規則算出來的數字；「等於模擬」由驗收 1（W2、W4）、G13 實跑與兩座造城逐日比全部建築（含墓碑）來證。
- 驗收 7(c) 寫「排到合併之後 → 同日合併的墓碑屋齡對不上」：實際不會是屋齡對不上——同日被吸收的房子在 `s.root` 裡已經不在，`syncCity` 對編號時直接丟例外；
  沒有同日重疊的軌跡（W2）則只能靠「每天的事件順序」檢查抓到（7 天順序錯）。
